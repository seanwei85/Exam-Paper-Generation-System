**版本**：V1.18
**日期**：2026-11-05
**依据**：产品需求文档 V1.22
**目标**：交付一个双击即用的本机程序，数据存本机 SQLite 文件，离线可用；导入侧可选联网 AI 兜底
**本版新增**：P40 文件夹版 exe 打包与软件内退出（FR-ST-12，详见文末 P40 节）；P39 设置页按身份裁剪与接口口径收口（FR-ST-11，详见文末 P39 节）；P38 会话时长与"在线"判定同源；P37 退出登录常驻入口与过期提示纠偏；P35 局域网多用户与岗位授权（账号按一级分类授权、同分类互斥写、管理员被动只读、组卷按范围收窄）；P36 多用户界面接入（登录页、用户管理页、多人协作开关、只读条、占用标记，详见文末 P36 节）

## 1 技术方案定稿

| 项 | 选定 | 原因 |
|----|------|------|
| 界面 | 原生 HTML + CSS + JavaScript 单页（无框架） | 无需联网加载依赖，体积小，打印样式可控 |
| 服务 | Python 标准库 `http.server` | 本机无 pip 网络，只能用标准库；单进程足够 |
| 数据 | SQLite（`sqlite3` 标准库） | 10 万题无压力，单文件可复制，事务可靠 |
| 导入解析 | Python 标准库自研（`zipfile` + `xml` 解 docx/xlsx，`zlib` 解 PDF 流） | 不依赖第三方库 |
| AI 识别 | `urllib` 直连 OpenAI 兼容的 `/chat/completions` | 不加 SDK 依赖；换服务商只改地址和模型名 |
| 启动 | `启动试卷系统.bat` → `pythonw server.py` → 自动打开浏览器 | 双击即用，无黑窗 |

**约束**：本机无法联网安装第三方包，因此不引入 pdf.js、openpyxl、node 等依赖，全用标准库实现。

**PDF 的两条边界**（`pdftext.py`，自研）：

- **能读**：文字层里的字——ToUnicode CMap（中文）、简单字体的 `(text) Tj` 字面量、Type0 双字节码、对象流（ObjStm）里的对象。页序走 `/Pages` 的 `/Kids`，换行按文本矩阵纵坐标判断。
- **不读**：版面重建（多栏、表格、图文混排）、图片（扫描件）、加密 PDF。前三者的收益远低于成本，第四者直接报错让人解密码。

**AI 的定位是兜底，不是主力**：`auto` 档先跑本地规则，拆得出来就不发请求。原因是用户手上多数文件本来就规整，全走模型既慢又按字数计费；真正需要模型的只有"版式乱到规则抓瞎"那一小部分。

## 2 阶段划分与验收

### P0 骨架与数据层

**做**：目录结构、`server.py` 静态服务与路由框架、SQLite 建表、初始化五大类与二级分类、每日自动备份、`启动试卷系统.bat`。

**交付物**：能双击启动，浏览器打开空白框架页，数据库文件已生成，含默认分类。

**验收**：删掉 `data/` 重新启动，自动重建库与分类；连续启动两次不报端口占用。

### P1 题库与单题录入

**做**：题库列表（筛选、分页、排序）、单题录入表单（五种题型动态切换、空数自动统计、建议分值、实时校验）、编辑、删除、批量操作、示例题库（约 40 题，覆盖五类五题型）。

**交付物**：可完成"录一题 → 出现在列表 → 改一题 → 删一题"闭环。

**验收**：五种题型各录 2 题全部成功；非法输入（单选给两个答案、多选只给一个、答案不在选项内）被拦截并提示具体原因。

### P2 电子题库识别导入

**做**：文件上传、四种格式解析（xlsx / docx / txt / 文字型 pdf）、题号切分与字段识别、识别结果预览编辑、确认入库、失败清单、Excel 模板下载。

**交付物**：导入一份 20~30 题的真实文档，识别后人工微调即可入库。

**验收**：自建 25 题混合文档（含单选/多选/判断/填空/问答），题型、难度、答案识别正确率 ≥ 90%；扫描件 PDF 给出明确提示不崩溃。

### P3 组卷引擎

**做**：组卷参数页、实时校验（题量够不够、积分可行区间）、难度积分分配到易/中/难、按题型抽题、缺口报告、试卷编号（MOLab-YYYYMMDD-NNN）、随机种子、快照落库、逐题改分与一键配平。

**交付物**：能从零参数生成第一套完整试卷数据。

**验收**：默认 100 分模板连续生成 10 套，每套总分 100、题量 60、难度积分精确等于 40；人为把某类题删到不足，系统拒绝出卷并报出精确缺口。

### P4 试卷与答案卷输出

**做**：卷面渲染（单位、标题、编号、时间、总分、时长、密封线、考生信息栏、大题分组、题号连续、分值标注）、A4 打印样式与防跨页、答案卷、试卷库台账、重新打印、导出 Word。

**交付物**：可打印的 A4 试卷与配套答案卷。

**验收**：打印预览无题目与选项被拆页；页码正确；答案卷题号与试卷一一对应；重启程序后重新打开历史试卷内容不变。

### P5 设置与数据维护

**做**：分类维护、单位名称与编号前缀、默认时长、数据备份与恢复、数据库统计、打开数据目录。

**交付物**：用户可自行改分类与单位信息，可一键备份到 U 盘。

**验收**：备份后清空数据再从备份恢复，题目与试卷数量、内容完全一致。

### P6 整体测试与交付

**做**：按需求文档第 10 章 16 条验收项逐条自测；接口级自动化脚本；修复缺陷；写使用说明。

**交付物**：可交付版本 + 一页纸使用说明。

**验收**：16 条验收项全部通过，含"重启电脑数据不丢""积分误差为 0""编号唯一"。

## 4 主要风险与对策

| 风险 | 影响 | 对策 |
|------|------|------|
| 扫描版 PDF 无法提取文字 | 用户以为坏了 | 检测到无文字层时明确提示"扫描件需 OCR，请用 Word/Excel"，不静默失败 |
| .xls 旧格式（非 xlsx） | 打不开 | 提示另存为 .xlsx，界面写明支持格式 |
| 填空题空数不统一 | 总分偏离 100 | 生成后显示差额，一键配平；模板按平均 2 空估算 |
| 浏览器打印分页差异 | 题目被拆页 | 用 `break-inside: avoid` + 每题块级包裹；提供打印自检页 |
| 本机无 Python 环境 | 无法启动 | 交付前检测 `python`，缺失时给安装说明；或后续打包 exe |
| 数据目录被误删 | 数据丢失 | 每日自动备份 + 设置页显示数据路径 + 一键备份到外部目录 |

## 5 实施顺序

先跑通主干（P0 → P1 → P3 的最小版本 → P4），让"录几道题就能出一套卷"尽早可用；再补 P2 导入（工作量最大）与 P5 设置；最后 P6 全量验收。

理由：导入解析是最不确定的部分，放在主干验证之后，避免卡住整体可用性。

P11~P15 是响应"已有存量试卷格式不统一、不想逐份重排"做的导入改造：本地规则继续做主力，AI 只做兜底。

- **P11 配置与连通**：密钥只落 `data/ai.json`，接口与界面一律脱敏（只露末 4 位），密钥框为密码类型且不回填；留空表示不修改，清空要显式点清除；连通失败时把上游原文带出。
- **P12 抽取与降级**：按题号行切块（不硬切字符，避免把题干和选项劈到两块），容忍 ```json 包裹与前后废话，某块失败二分重试、仍失败则该块回退本地规则并记块号；部分成功时保留成功的结果并标 `ai+local`。
- **P13 PDF**：文字版直接抽文字层（页序走 `/Pages` 的 `/Kids`、换行按文本矩阵纵坐标、支持简单字体字面量 `(text) Tj`、Type0 双字节码、对象流 ObjStm）；扫描件判为 `scanned` 并给"导出成图片"的下一步；加密与假 PDF 报可读的错。拆题前先整行删掉页眉页脚（`第 N 页 共 M 页`、`共 N 页`、`Page N of M`、`- 3 -`），因为题跨页时页脚正好卡在选项中间，留着会被拼进选项文本；「页」还要认兼容字「⻚」（U+2EDA），有些字体的字形表把它映射到部首区，正则只写「页」会漏。
- **P14 调度**：`auto` 先本地、拆不出来才动 AI；`ai` 全交给模型；`local` 零网络请求（有用例专门盯住一个请求都不发）。图片走多模态 data URL，格式不支持的（bmp/gif）不发请求直接提示转格式。
- **P15 界面**：识别方式三档可切换且被记住、拖入区认 PDF 与图片、未配置 AI 时指路到系统设置、设置页四件套齐全、页面源码里搜不到完整密钥。

P20 是真实文件验收第二轮暴露的：《机房运维试题及答案.pdf》每页就是一张整幅位图（FlateDecode + Indexed/DeviceRGB，PDF 里一个字体都没有），此前只能让用户"每页另存为 PNG 再逐张上传"——几十页的卷子没人愿意干。

关键判断：**这类文件不需要 PDF 渲染器**。页面图本来就是内嵌的 XObject，zlib 解压 + 调色板展开就能拿到像素，PNG 用 zlib+struct 现写，纯标准库即可；真正要小心的是方向——PDF 用户空间 y 轴朝上、位图行序朝下，排版软件普遍写负的 d（这份是 `595.2 0 0 -770.4 0 806.13 cm`），照原样导出会得到上下颠倒的卷子。

实测结论（同一份文件）：本地文字层抽不到任何字符，只能走视觉通道。当天网关上的 DeepSeek-V4-Flash 明确回「我无法看到您提供的图片」，判断为"卡住的是模型，不是程序"；**10-26 换 Kimi-K3 复测推翻了这个判断**——K3 能看图，软件全链路识别出 2 页 12 题（单选 10、多选 2，均带答案，`by=ai-vision`）。真正卡住的是两件更要紧的事，见 P21。

P21 是 K3 复测当场暴露的：**识别得了，但用户等不到**。

- **超时写死 120 秒**。K3 是带思维链的推理模型，一页真实卷子实测 **215 秒**才能吐出 JSON；两页必然全超时，重试也只是再等一遍（那次后台跑了 12 分钟才报错）。更糟的是超时后的提示是"如果模型本身不支持看图…"——把用户引向换模型，而真正该做的是把超时调大。默认值改为 **300 秒**，下限 30（填 0 或负数按默认兜住，不然等于一个请求都发不出去），并把它搬到设置页上——只写在 `data/ai.json` 里等于用户改不了。
- **同步请求没有进度**。解析是一次阻塞的 POST，模型在想的时候连接上没有新字节，界面只能显示一句"正在让 AI 识别…"。一页三分钟、整份十几分钟，看起来就是卡死，用户只会去关页面。做法：解析侧往一张内存登记表里按页/按块写「第 i/N」，界面每 1.5 秒查一次 `/api/import/progress`；成功、失败、异常三路都收尾（留一个永远 running 的任务比不显示更糟），过期任务顺手清。
- 顺带修正一句判断：**推理模型的慢是常态，不是故障**。软件能做的只有如实显示进度 + 让超时可配，不要去猜模型的耗时。

关键取舍：进度用"另一个请求轮询"而不是改成长连接或任务队列——`ThreadingHTTPServer` 本来就并发，加一张字典就够；改成异步任务会把导入结果、重复判重、前端状态机一起改，收益不匹配。

P22 是用户真实使用反馈带出来的："批量导入后，选择题有题干、没看到选项"。排查结论：**数据没丢**——
库里 48 道选择题全部有选项，导入预览表也有选项列；丢的是**题库管理列表只显示题干**，用户在列表里
确认不了选项是否导进来了。修法是在列表题目单元格的题干下加一行小字选项摘要（`A. xx` `B. xx` …，
超长截断），选择题一眼见选项，问答题/填空题不显示；预览弹窗保留。用例两条：列表里能看到 `A.`/`B.`、
选项行的有无与题型一一对应（非选择题不许出现选项行）。

P23 回答用户的一个问题："AI 模型的技术要求，在哪个界面提醒比较好"。结论是**两处各管一头**：
设置页常驻技术要求（配置时必看，选错模型第一时间知道原因而不是等失败后排查）——读扫描件/图片 PDF

P24 是第三轮真实入库当场撞出来的，**六处都不涉及 AI，全是本地规则漏认的版式**：

- **○● 标记**（答题解析导出）：● 是正确项、○ 是错项。原来两个都不认，75 道有答案的题全成草稿，
  还把「●」留在选项正文里；每道题后面的「回答正确（+1分）」也粘进最后一个选项。
- **一行多选项**：`A. 5500*1400   B、5500*1600  C、6000*1600`——只认出 A，另外三个成了 A 的正文，
  阳光电源 17 题里 12 题选项报废。拆的时候按 A→B→C 递增对齐，句子中间的「A、B 两类」不切。
- **答案在题干行尾**：`……副边三相电压为    。答案：B`，原来只在独占一行的答案行里找。

- **分类关键词**：界面写着"题干里出现电气/暖通…会自动归类"，文本路径其实一直没做（只有表格路径做了）。
  现在按设备词猜（冷机/空调→暖通，UPS/配电→电气…），猜不出留空给界面兜底——宁可不猜。

验收方式：11 条纯函数用例（不联网、不起服务），加上真实文件复检——
数据中心 docx 答案缺 80→14、电气 docx 52→6、阳光电源选项异常 12→0。

P30 是用户提出："为什么不在软件层面增加类似 WorkBuddy 处理 PDF 的功能，然后喂给普通 AI 模型，这样 AI 的模型兼容性就更好了。"

方向完全正确，但要先拆穿一个概念：**"软件层面处理 PDF" 的最后一步永远需要一个能认字的东西**。
文字版 PDF 我们早就自己解（P19/P22，零 AI）；图片型 PDF 缺的是"像素 → 文字"这一步。WorkBuddy 是
云端产品，这步靠服务器上几百 MB 的 OCR 模型；单机软件不走网络，就得在系统里找现成的识别引擎——
而 Windows 10/11 恰好内置（Windows.Media.Ocr），有中文语言包就能用。于是图片型 PDF 有了第二条路：

    页面图（本地解码 0.3 秒）→ 系统 OCR 认字（约 2 秒/页）→ 现有本地规则拆题

实测对比：同一份两页卷子，视觉模型约 430 秒（Kimi-K3），OCR 通道 4.5 秒，**快两个数量级**且零 token；
12 题拆出 7 题（题号被认成 "I."/"生"、选项字母认成小写 "c."、选项换行错位），视觉模型降级为兜底。

**假空格清理此前只跑在单元测试里，链路没接线**：`_despace` 有单测、没被 `ocr_png_bytes` 调用，真机
输出是"机 房 温 度"这种形态，467 个字只拆出 2 道题。现在清在 OCR 出口（第 1 页 263 字），并补了
两条用例锁住链路（`OcrSpaced` 端到端 + `test_ocr_output_is_despaced`）——教训是：只在单测里调用过的
函数，等于没接。

**视觉模型选型（2026-10-27 实测，同一张扫描页 + 生产提示词，2 页 12 题真值）**：

| 模型 | 能否看图 | 题数 | 有答案 | 耗时/页 | token/页 |
|---|---|---|---|---|---|
| DeepSeek-V4.1-Flash | ✅ | 6/6 | 5（第 6 题答案在下一页，正确） | **22 秒** | 1950 |
| Kimi-K3 | ✅ | 6/6 | 5 | 108 秒 | 3070 |
| GLM-5.3 / DeepSeek-V4-Flash / 021SFM-Instruct / 021SFM-Thinking | ❌（分别回复"无法处理图片""请上传图片"、HTTP 400） | — | — | — | — |

即网关 6 个模型里只有两个能吃图，**DeepSeek-V4.1-Flash 比 Kimi-K3 快约 5 倍、省约 40% token，质量相同**。

**token 账（同一页，文字 vs 图片）**：图片输入 1159 / 文字输入 543，图比字每页多约 600 token；
但输出 JSON 才是大头（700~2000），两条路径总量基本持平（1949 vs 2019/页，±5%）。所以"图片型走视觉
模型"并不比"OCR 文字走模型"贵，真正该做的是**把 OCR 文字交给模型整理**——同样是 12/12，而且
不挑模型，GLM-5.3 这类纯文本模型也能干。本地规则硬啃 OCR 文本（7/12）才是短板所在。
工程上有三处值得一提：

1. **WinRT 类型在脚本文件模式下不自动投影**——`[Windows.Media.Ocr.OcrEngine]` 直接用会
   TypeNotFound，必须先以 `[Windows.Media.Ocr.OcrEngine,Windows.Foundation,ContentType=WindowsRuntime]`
   显式预加载；
2. **宿主脚本双引号字符串里 "`1" 的反引号会被吞掉**，泛型名 `IAsyncOperation\`1` 永远匹配不上，
   报 "Cannot index into a null array"——用单引号字符串才稳；
3. **OCR 在汉字间插假空格**（"机 房 温 度"），按"两侧均为半角才保留"清理，否则题干没法看。

P31（FR-IM-29）把上面这些实测结论落成路由。用户先查证 DeepSeek-V4.1-Flash 官方具备原生视觉能力，
再拍板两条规则：**成功率优先（确认能看图就直接看图）、判断过程要在界面可见、预估剩余时间动态更新**。
设计要点：

- **视觉能力不能看名字猜**：V4 与 V4.1 就差一个点、一个能看图一个不能；网关部署方还可能对同名模型做
  不同配置。判定只能来自"此刻的实际行为"——发一张写着 AB12 的 100x40 小图，**回答内容里有 AB12 才算过**
  （V4-Flash 实测收图后回 HTTP 200 但内容是"请上传图片"，图被静默丢弃，只看状态码必被骗）。结果连同
  模型名缓存进 data/ai.json（vision_ok/vision_checked），换模型自动失效、网络错误不缓存；
- **双路兜底**：确认能看图→逐页直接看图，半路失败自动降级"本地 OCR 认字→AI 整理"；确认不能看图直接走
  方式1；OCR/AI 都没有才退本地规则（7/12，最后一条防线）。`_scanned_pdf_route` 统一收口，
  local 档保持零网络（OCR→本地规则）；
- **进度与预估**：探测/认字/交给 AI/直接看图/降级各阶段都有文案，进度对象新增 eta_sec 与 elapsed，
  前端按已完成项的实际耗时动态估算"预计剩余约 N 分钟"（不足 5 秒不显示，首项跑完前提示"首项最慢"）；
- **测试注入**：视觉探测走 tests/fake_ai.py 的可编程应答（正常回 AB12 / 回"请上传图片" / 500 三态），
  进度预估用假脚本 fake_ocr.ps1 的延时模式；P20/P21 走视觉路径的用例在配置里显式写入
  vision_ok=true（相当于探测已完成），避免每条用例都真发探测请求。

另修一处用户反馈的显示缺陷（2026-10-28）：导入「识别结果」表的选项列只显示选项**个数**（一个数字），题干有内容、选项内容却看不到，识别质量没核对就入库——与 FR-QB-11 修题库列表是同一类问题，当时只修了题库页漏了导入确认页。现改为与题库页同款的选项摘要行（超长省略、悬停看全文），加宽选项列，并补 1 条用例。

另修 P29 一处用例竞态（与本版功能无关，全量回归时暴露）：AI 审校收尾会 route() 异步重渲染题库页，
断言 aiBtn 前要等重渲染完成，否则偶发"按钮还没回来"的 null——等元素出现再断言，断言本身不变。

测试注入也换了路数：服务端是子进程，进程内 monkeypatch 够不着，改用环境变量把识别脚本换成假脚本，
行为由环境变量切换；真机冒烟用例只在检测到本机引擎时运行（skipUnless），无引擎环境自动跳过。

P29 是用户提出："AI 评审多个题目时能不能增加暂停和继续的按钮？"

功能本来就能停——问题在**多久停得下来**。原先界面十题一批提交，点暂停得等这一批十题
全跑完才轮得到判断，推理模型一题几十秒，那就是十几分钟；按钮挂着，按下去没有反馈，
等于没有。所以这一阶段的关键改动不是加按钮，而是**把批量提交从十题一批改成逐题提交**：

- 本地环回多发几个请求没有成本（不联网、不经网关），换来暂停粒度从"一批十几分钟"
  缩短到"一题几十秒"；
- 顺带单题失败只连累一题，不会因为一批里有一个超时就把这一批其余结果一起丢掉；
- 已发出的同步请求仍然掐不断——掐断等于白花钱，服务端也收不了尾。所以暂停的语义是
  "不再发新请求，手上这题跑完为止"，界面必须把这句话说出来，而不是假装立刻停住。

细节上两处容易做错：

1. **暂停要显示成两种状态**："正在审的这一题跑完就暂停" 和 "已暂停"。混成一句话，
   用户看到"已暂停"会以为停了，其实还在付钱。所以进度条按 `paused && waiter` 分别措辞。
2. **继续必须从断点续跑**。重跑已完成的题不只是拖时间，还会覆盖掉已经生成的建议。

P28 的起点是一条用户反馈："随机找了 2 个缺答案的试题点 AI 校审，显示 not found。"

代码没有错，用例 390 项全绿。错在**跑起来的那份是旧代码**：
界面 `ui.html` 是磁盘文件，刷新即生效；后端在上午 09:22 启动的进程内存里。
新界面配旧后端，新按钮必然 404。而用户没有任何线索——界面照常打开、题库照常显示，
只有新功能静默失效；他按提示"重开软件"，启动脚本一看到端口在监听就只打开浏览器然后退出，
旧进程纹丝不动，于是"重开"变成了空操作。

这类缺陷测不出来，因为自动化用例都自己起服务、跑的都是最新代码。所以这一阶段不做功能，
只做三件"让错误自己暴露"的事：

1. **后端能自报身份**：启动时给源码拍时间戳快照，请求时与磁盘现值比较（1 秒容差），
   `/api/version` 直接回答 `stale` 还是 `fresh`；`?plain=1` 给脚本用，省得解析 JSON。
2. **界面把话说清楚**：stale 时页面顶部固定黄条，写明"运行的还是旧版本、新按钮会报 not found、
   请先停止再启动、题库不受影响"；设置页常驻显示版本与本次运行时刻，随时可核对。
3. **启动脚本不再把"端口有人监听"当成"软件已就绪"**：先问一句 `fresh`，非 fresh 就换新；
   换新前核对占用者进程名含 `python`，端口属于别的软件时一律不杀。另外脚本必须用 CRLF，
   LF-only 的批处理在 cmd 里找不到 `goto` 标签，表现为窗口一闪而过、什么都没启动。

顺带把"前端调用的每个 `/api` 路径后端都必须存在"做成用例（AC-20）。这才是 404 的直接来源，
以前靠人眼比，现在提交前就会红。

P25~P27 是用户提出的："有些试题没有答案或没有解析，能不能用 AI 推荐答案和解析；有答案的也让它先检查一遍，给出建议。"
两个功能都做，但**放在题库页，不放在导入环节**——这条取舍值得写下来：

- 导入的职责是忠实搬运（FR-IM-13 明写"材料没给答案就留空，绝不编"）。AI 在导入时顺手补答案，
  会让"来自文件"和"模型编的"混在一起，日后查不出某道题的答案到底是谁写的；
- 推理模型识别一页真实卷子要 200 秒上下（P21），批量导入时再插一轮审校，时长直接翻倍；
- 缺答案的题本来就是草稿、不进组卷池（P17），放在题库里补是安全的待办清单，补到哪儿算哪儿不影响出卷。

三条防线是这一阶段真正的设计内容，不是为了防御而防御：

1. **采纳前不动库**。建议独立存一张表、自带状态机（待处理 / 已采纳 / 已忽略），题目表在用户点头之前一个字都不改。
   采纳也只改用户点的那几项：只采纳答案时解析保持原样。
2. **建议必须机器可校验**。选项范围、判断题归一、填空空数、单选单答案，四条逐项过；不合规的只展示不许采纳，
   界面置灰 + 接口层再拦一次。一个落在选项外的答案比没有答案更坑人——它有答案的样子，能进卷子。
3. **自相矛盾降级为存疑**。模型说"不一致"却给出与原答案相同的答案、说"一致"却给了另一个答案，
   这不是结论而是噪音，一律按 unsure 处理。

补上撤销采纳（FR-AI-02）：采纳是人工点头，但人工也会点错。采纳那一刻把原答案与原解析留档，
「撤销采纳」只回滚这两项——多改一个字段就是新的破坏。为此 `ai_review` 表新增两列，
正式库里已经有几百道题，所以 `init_db()` 里加了 `_migrate_ai_review()` 做 ALTER 升级，
并有一条用例专门造一个"老结构表"，验证升级后既有题库不被清空。

P19 解决的是「读得出字节、解不出文字」的最后一种：方正等老排版软件导出的中文 PDF，Type0 + Identity-H 编码、字体不内嵌、没有 /ToUnicode，文字层抽出来全是 2 字节 CID 乱码。

关键发现：这类字体的 /CIDSystemInfo 标明 **Adobe-GB1 字符集**，CID→Unicode 由官方 CMap （UniGB-UCS2-H）定义，**不需要 AI**。做法：把官方表（28625 条）压缩成 104KB 内嵌到 `gb1map.py`（纯标准库解码），`pdftext._fonts_of` 在无 ToUnicode 的 Type0 字体上回退到这张表；`pdftext.extract_pages` 顺手剔除页首/页尾的孤立页码行（否则页 1 的「1」会把卷头标题吞进题干）；`importer` 新增 STD_RE（「标准号: 《规范》YDxx ◆题干」开新题、出处进题干，规范名认《》和 <<>> 两种）、行内粘连切分（一行物理文本粘着两条时按「标准号:」切开逐段喂）、▁（U+2581）挖空识别为填空。

金标准比对（用户提议、也是防退化锚）：那份 PDF 的人工核对结果存 `tests/fixtures/gb1_golden.txt`（67 题），用例断言软件解析与金标准的匹配率 ≥90%。修完实测：摸底工具对这份 PDF 的结论从「要开 AI」翻转为「能读，65 题整份没答案（草稿流程）」——**8 份存量文件全部能读，AI 一分钱没花**。

教训两条：①探路时造的 pdf2png.py（无头 Chrome 截 PDF 页）没派上用场，删除——正解是映射表不是截图；②unittest 复跑三次同样失败而手工脚本正常，最后发现是测试自身的 norm/split 顺序写反，不是缓存问题——改测试前先怀疑自己的测试。

真实文件首轮摸底（7 份）暴露出一个厂商模板版式：**题号独占一行**（表格里题号一个单元格）、**答案直接写在题干括号里**（`蓄冷池（ B ）m³`）、且**多张工作表各自从 1 重新编号**。`split_questions` 新增 SEQ_RE（孤立数字行按接续序号认，例外是「1」在上一题已完整时重新开题）与 INLINE_ANS_RE（题干括号内纯选项字母/判断标记即答案，多处括号歧义时不猜）。暖通 xlsx 从 21 题修到 31 题、28 题带答案；《综合理论试题.doc》缺答案从 89 降到 56。摸底工具另加**乱码 PDF 检测**：老排版软件导出、字体没带 ToUnicode 映射的 PDF 抽出来几乎不含汉字，不仅读不出题还会从乱码里捡出垃圾题——现在直接判「要开 AI」并把原因写进报告。

另配了一个**验收摸底**小工具（`tools/probe_import.py` + `机房运维试卷系统/验收摸底.bat`）：把存量题库文件丢进 `待验收样例/` 目录、双击 bat，就逐份试读并生成 `识别报告.html`——每份文件能拆几题、几题缺答案、要不要走 AI、前两题题干长什么样，一眼看完，**全程只读、不写库**。它的意义是把"你的文件能不能读"这件事从"导进去才知道"提前到"导之前就知道"：单测里的 doc/xls/PDF 样本都是自己构造的，只能证明格式解析没写错，证明不了用户手上那份文件能读出来。工具自身也有 3 条用例盯着（bat 指向、报告能生成且不误读说明文件、图片要引导到 AI），因为报告模板里混 CSS 时被 `100%` 噎住过一次——控制台全绿、最后一步生成报告直接抛异常。

P18 把需求书里一直没验的 AC-14 补上：铺满 1 万题再测，组卷（自动与配额两种模式）必须 2 秒内完成，预检、列表、关键词与分类筛选、工作台统计各给 1 秒。实测这台机器上万题组卷约 0.27 秒、列表 4ms、统计 35ms，余量很大——但用例的意义是防退化：一旦 `load_pool()` 被改成"先全表取出再在 Python 里筛"，或者新加的筛选条件漏了索引，这里就会立刻红。阈值按需求书原话取 2 秒，其余 1 秒，留足老办公机的余量。

P16 解决的是"文件根本读不开"这一层——用户手上的存量题库大量是 `.doc` / `.xls`（厂商模板导出、老 Office 另存），不是标准 OOXML。纯标准库自己实现了 OLE2/CFB 容器（512/4096 扇区、FAT/DIFAT、目录项、MiniFAT 迷你流）、BIFF8 的 SST 与单元格记录（含跨 CONTINUE 的字符串）、Word97 片段表（压缩片段按 GBK、非压缩按 UTF-16LE），外加 RTF 与 HTML 表格嗅探。要点：

- **按内容嗅探而不是看扩展名**：`html 表格存成 .xls`「文本改后缀的 .doc」都要能给出一句能照着做的错，而不是抛 `BadZipFile`；
- **按真实格式纠正扩展名**：`.xls` 实为 xlsx/zip 时说"重命名为 .xlsx"，`.doc` 实为 docx 时同理；
- **多工作表**：第二张表重复的表头行必须剔掉，否则会变成一道题干为"试题正文/参考答案"的怪题；
- **Word 域代码**：`TOC \o "1-3" ...` 这类指令文本按域层级丢弃、只留域结果，否则目录指令会灌进正文；
- **行内选项**：题干单元格里写着 `A.甲 B.乙 C.丙 D.丁` 时要拆成选项，否则会变成"没有选项的选择题"。

P17 解决的是"题库根本没有答案列"。存量题库里有一批是面试/口试题库（开关电源、油机、蓄电池、高低配、UPS），答案在主管脑子里，原来一律要求答案非空，等于整份白导。现在的规则是允许入库但按草稿处理：组卷池**绝不抽**（卷子要附标准答案，抽到空答案等于出一份无法评分的卷）、题库页能一眼看出缺答案并可只看缺答案、补上答案后自动进池。同时保留"写了答案就必须合法"的校验——放行的是"空"，不是"错"。

其中三条打印断言不看截图、直接读 PDF：用自研的最小 CDP 客户端驱动无头 Chrome 走 `Page.printToPDF`，再用自研的 PDF 文本抽取器（`pdftext.py`，zlib 解流 + 解析 ToUnicode CMap + 文本矩阵断行）把每页文字取出来，断言"每一页都有『第 N 页 共 M 页』""没有侧栏与按钮文字""页数不多不少"。只用截图或 DOM 是测不出这些的——打印出来的 PDF 是另一套渲染结果。这个抽取器同时是产品里"导入 PDF"的实现，测试与功能共用一份，避免"打印读得出、导入读不出"。

P7~P10 是对着需求书逐条追溯后补的：需求书写了、代码没做（或只做了一半）的条目——打印页脚页码、题库排序缺「最近修改」、选项拖动排序、导出 Excel、批量改分类、单题预览、保存前查重、题库健康度、难度推荐值、试卷参数与种子、配额执行偏差表。每条先写用例跑到红，再改代码跑到绿。

其中 P4 的 4 个与 P2 的 6 个用例是端到端渲染测试：启动独立服务 + 无头浏览器抓真实 DOM，验证卷面编号、密封线、大题标题、填空空数标注、答案卷逐空答案、导入识别结果表等元素真实存在，不依赖人工看图。

另有 P2 的 12 个交互测试（`tests/test_p2_interact.py`）：用自研的最小 CDP 客户端（`tests/cdp.py`，纯标准库实现 WebSocket）驱动无头 Chrome **真点按钮、真改输入框**，断言"删掉一行后行数与勾选数同步、缺答案标黄并可入成草稿、缺题干被拦下、失败原因页内列出、最终 6 题真的进库"。`--dump-dom` 只能拿静态 DOM，这类行为用它是测不出来的。

渲染断言统一剥离内联 `<script>` / `<style>` 后再做匹配。原因：页面模板字符串本身就含"识别结果""共 N 空"等字样，直接对整份 DOM 做字符串计数会把源码当成渲染结果，让断言假性通过。

### 6.1 实现过程中的关键缺陷与修复

| 缺陷 | 影响 | 修复方式 |
|------|------|----------|
| 难度分解未考虑各难度实际可用量 | 抽题中途凑不齐，出卷不足题量 | 难度 DP 加入可用量约束，改为按题型×难度求解 |
| 缺失难度键被当成"不限制" | 多选题没有易题却分配了易题，导致整类抽空 | 缺失键按 0 处理 |
| 必考锁定题难度余量为 0 时被跳过 | 锁定题没进卷 | 占用同题型其他难度的名额 |
| 数据目录参数在双模块下失效 | 指定数据目录后仍读写正式库 | 路径解析移到模块加载期 |
| 服务端口被占后连到旧实例 | 测试读到另一份数据 | 动态分配端口 + 校验数据目录 |
| 导入页 `?demo=1` 参数未被消费 | 解析成功后路由再次命中 demo，对解析接口形成循环请求，页面上"正在解析…"与结果表并存 | 进入示例分支时用 `replaceState` 摘掉参数，demo 只消费一次 |
| 识别结果表渲染在两个位置 | 勾选/改分类后页面出现两份表 | 结果表统一由 `#impStage` 容器承载，删除页面尾部那份 |
| FR-IM-09 模板下载未实现 | 用户没有"照格式填"的入口，导入成功率依赖自行摸索格式 | 新增 `importer.template_xlsx()` 与 `/api/import/template`，纯标准库生成 xlsx（五题型示例行） |
| FR-IM-02 按表头取列未实现 | 把表格行转纯文本再正则拆题，表头行会被当题干，"下载模板→填写→导回"这条路径是断的 | 抽取 `_xlsx_rows` 保留列位置，按列名映射字段（支持别名、列顺序任意、缺题型列可推断），无表头时才回退到文本模式 |
| 选项顺序按列位置排 | 列顺序打乱后选项变成 C/A/B，与标号语义不符 | 改为按 A~H 标号排序 |
| 分类下拉显示默认值但没写回数据 | 表格里看着是"电气"，提交时 cat_id 为空，后端报"未选择一级分类"，示例 6 题只入库 1 题 | 解析后统一 `impNormalize()` 把显示值写回；补充二级分类列并随一级联动 |
| 入库结果用 alert 弹窗 | 部分题失败时弹阻塞对话框，页面卡住，也无法自动化验证 | 改为表格上方内联清单，列出题干与具体原因，失败的题自动取消勾选，留在本页继续改 |
| 重复判定未考虑格式差异 | 从别处复制来的题「（　）」变成「( )」就判不出重复，等于判重形同虚设 | 比对前归一化：全角转半角、去空白、去括号占位与下划线；归一化后不足 6 字的不参与，防短语误判 |
| 极短题干互相误判 | 若不做长度下限，"机房温度"这类四字题干会彼此相似 | 设 `MIN_LEN=6`，并加长度比、字符集重合度两道粗筛 |
| 导入记录只存在内存里 | 重启即丢，等于没留档 | 落在 `import_log` 表；空提交不写，全部失败要写 |
| 打印时 `@page` 边距设成 0 | 侧栏、页头、按钮被印上试卷，页脚也没有落脚处 | 页边距交给 `@page`，页脚用 `@bottom-center` 的 `counter(page)/counter(pages)` 生成；界面元素统一 `display:none!important` |
| 判"末尾多一页空白"其实是抽取器的错 | 目录对象里含 `/Pages 2 0 R`，被当成一个页面对象 | 页面识别改为 `re.search(rb"/Type\s*/Page(?![A-Za-z])", body)`，抽取页数与 PDF 里 `/Type /Page` 计数对齐 |
| `/api/questions/export` 返回 500 | 路由顺序问题：被 `/api/questions/<id>` 前缀分支先吃掉，`int("export")` 抛异常 | 导出分支放在前缀分支之前 |
| 批量改一级分类不改二级 | 出现「电气 + 暖通某二级」这种库里不存在的组合 | 改 `cat_id` 时一并写入该分类下的第一个二级；改 `sub_id` 时反查 `cat_id` |
| 查询条件在列表与导出里各写一遍 | 两边筛选逻辑会慢慢跑偏，"导出的和看到的不一致" | 抽出 `_q_where(params)`，列表与导出共用同一份条件 |
| 查重塞在 `save_question` 里 | 核心写入函数变成"相似就拒绝"，导入入库、脚本补题、单元测试全被拦下 | 查重上移到接口层 `create_question`；`save_question` 只管校验与写库，导入入库不再被误伤 |
| 测试的导航序号写成了实例属性 | 每个用例都从 1 开始，第二个用例的 URL 与第一个完全相同，Chrome 只换 hash 不重载，断言打在上一份数据上 | 序号挪到类级 `_nav_seq`（`tests/renderbase.py` 的 `nav()`），并把 p2/p7/p8/p9 统一改成调用它 |
| `答案解析：…` 被当成答案行 | 单选答案 A 被"解析文字"顶掉后又因不在选项范围内被清空，整题变成缺答案 | 解析行先判，答案正则加 `(?!解析)` 负向前瞻；兼容 `Answer/Analysis` |
| 跨页题的行内页脚被拼进选项 | 页脚正好落在选项中间，最后一个选项变成"…中水 第 2 页 共 8 页" | 拆题前整行剔除页眉页脚（`第 N 页 共 M 页`/`共 N 页`/`Page N of M`/`- 3 -`）；注意某些字体把「页」映射到兼容字 U+2EDA（⻚），正则要一并认 |
| 整份没答案列的题库逐题刷警告 | 215 道题刷出 215 条提示，真实问题被淹没 | 全部缺答案时合并为一条汇总提示；仅少数题缺答案时保留逐题提示（那时逐条更有用） |
| 第二张工作表的表头变成一道题 | 多工作表题库里出现题干为"试题正文/参考答案"的怪题 | `_drop_repeated_headers()` 在拆题前剔除重复表头行 |
| Word 的目录域代码灌进正文 | `TOC \o "1-3" \h \z \u` 变成题干的一部分 | 按域层级丢弃指令段、保留域结果 |
| 测试侧 `tests/pdftext.py` 与产品模块同名 | `import pdftext` 导入到自己，抽取用例整组报错 | 删掉测试侧副本，统一引用产品模块——同一份实现，才能保证"打印读得出、导入读不出"这类问题被测出来 |
| AI 超时写死 120 秒 | 推理模型识别一页要 215 秒，整份扫描件的视觉通道必然全超时，且报错指向"模型不支持看图"，把用户引向换模型 | 默认改 300 秒、下限 30，设置页可改（FR-IM-24）；错误提示区分"超时"与"模型看不了图" |
| 导入没有进度 | 一页三分钟、整份十几分钟，界面只有一句"正在让 AI 识别…"，看起来是卡死，用户会去关页面 | 解析侧按页/按块上报「第 i/N」，界面轮询显示；结束与失败都收尾（FR-IM-25） |
| 测试里替换 `chat()` 后没还原 | 后续用例拿到被替换的函数，出现"单独跑绿、全量跑红" | 模块级只保存一次原函数，替代品按子类隔离 |

## P32 圆点选项版式（2026-10-28，用户反馈第三轮）

用户在题库管理里发现大量无答案草稿题"选项都被识别进题干"。排查结论：**不是识别错，是版式没覆盖**——
《数据中心值班专员测试题—翁晓宁.docx》是"答题解析"平台的导出，选项不用 A. B. C. 而用圆点标记
（○ 错项、● 正确项），其中两类此前认不出：

1. **无字母圆点选项**：「○12」「●36」——OPT_RE 要求圆点后必须跟字母；
2. **字母选项用逗号分隔**：「●A, 电池失效;」——分隔符类里没有逗号。

认不出选项的题被当成问答题，选项全部留在题干里且答案（● 标记）丢失 → 全成草稿。
修复：OPT_RE 分隔符加 `,，`；新增 CIRC_OPT_RE（行首圆点 + 内容 = 选项，字母自动编 A/B/C…，
实心圆计正确项；要求题干已存在、选项未满 8 个，防误吞正文）；flush 时**题目带 ≥2 个选项的一律
按选择题定类**——段落标题写"问答题"也不能把带选项的题按成 qa（以数据为准）。

真实文件验证：80 题全部正确拆分（60 单选 + 20 多选），● 答案全部带出，0 道残留圆点。
数据修复：备份后删除两批共 29 条错判 qa（全库按"qa 且题干含圆点"精确筛出），重导该文件——
66 条与库中好题重复被跳过，14 条以正确形态补回（全部带选项与答案）。

## P33 审校建议附原文出处（2026-10-29）

起因是用户看到 SurfSense 的"答案带引用"。我们的审校建议原本只有一个结论 + 一段理由，
用户只能信或不信；P32 那批"选项被吞进题干"的错题恰好说明问题——题目本身已经错形，
模型照样能给一个看起来合理的答案，没有第二参照点就发现不了。

两层出处，缺一不可：

- **数据来源**：导入入库时记录 `question.src_file` / `src_page`。页码只有逐页解析的路径
  说得清（视觉逐页、单页 OCR）；文字层整篇解析、多页 OCR 合并后已无法归属，留 0，
  界面按"只到文件级"显示。更新题目时不覆盖来源——改题干不等于这题不是从那页来的；
- **模型引用**：提示词新增 `evidence` 字段，要求直接引用题干/选项/来源原句，
  来源里没有就写"来源中未见相关表述"，禁止改写成自己的话。`evidence` 与原有的 `reason`
  分开存：前者是引用、后者是推理，混成一段就没法核对。漏给 evidence 不算不可采纳，
  只是少一行引用——不能因为模型少写一个字段就把可能对的建议作废。

界面：建议卡片「原文依据」与「来源：文件 第 N 页」两行分开显示；编辑页题干下方显示来源，
核对原卷不用再翻导入记录。老数据没有来源就整行不显示，不写"未知文件 第 0 页"。

数据库：老库靠 `_migrate_source()` 补 `src_file`/`src_page`、`_migrate_ai_review()` 补
`evidence`——正式库 631 题在副本上验证过，升级后题数、建议数不变。

## P35 局域网多用户与岗位授权（2026-11-02）

**依据**：`doc/多用户管理需求草案_v0.4_定稿版.md`（FR-MU-01~13）。
单人单机扩到"几个人各写各的科目"，不改数据模型、不引第三方依赖。

### 分层

| 文件 | 职责 |
|------|------|
| `auth.py` | 账号、密码哈希、会话、分类授权、写占用表（进程内） |
| `auth_http.py` | 鉴权的 HTTP 无关编排：登录、whoami、用户管理、写闸门、首次初始化 |
| `server.py` | 只做接线：取会话 → 过闸门 → 调业务；组卷时注入授权范围 |

分成两层是因为 `auth.py` 需要被测试直接调用（规则落点在这里），
而 `auth_http.py` 里的东西全都跟"请求/响应"有关，混在一起会让单测被迫造 HTTP。

### 关键决定

- **只读接口也要登录**：分类树、统计、题库列表本身就是"看得见什么"的入口。
  只在界面上藏分类，改一个 `cat_id` 参数就能翻到别人的题，等于没做隔离。
  实现上在 `do_GET` 入口集中拦截（`_read_guard`），白名单只留探活、whoami、版本自检。
- **组卷范围走参数注入，不让引擎查库**：`paper_engine` 原本只认配置字典，
  单元测试直接传 cfg 就能跑。改为在 cfg 里注入 `allowed_cats`（None=不限），
  引擎据此收窄候选池与分类树。保持原契约，也避免引擎反向依赖会话。
- **分类结构 / 清库 / 恢复备份是管理员专属**，不走分类授权：
  这些操作动的是"别人的目录"甚至整库，按分类粒度授权没有意义。
  管理员在有普通用户在线时仍受只读约束，这里一并挡住。
- **会话过期顺手释放分类占用**：原先只删会话不清占用，别人会一直看到
  "该分类正被 XXX 编辑"，而那个人其实已经掉线，只能干等空闲超时。
- **首次初始化只开一个口子**：`count_users()==0` 时允许匿名建第一个管理员，
  其它动作一律拒绝；有账号后这条路立即关闭。
- **`bind_lan` 真的生效**：之前设置项存在但服务写死绑 `127.0.0.1`，
  等于开关是装饰。现在按设置决定绑 `127.0.0.1` 还是 `0.0.0.0`。

### 用例

`tests/test_p35_multi_user.py`（11 项）：

| 分类 | 覆盖 |
|------|------|
| P35Account | 密码哈希与校验、建号勾分类、登录换 token、token 反查、同分类互斥、跨分类并行、越权被拒、管理员被动只读、过期释放占用 |
| P35PaperScope | 预检拒绝未授权分类配额、真实组卷只抽授权分类 |
| P35Http | 未登录读 `/api/state` 被拒、首次初始化管理员且只能一次 |

## P36 多用户界面接入（2026-11-02）

P35 把后端的账号、授权、互斥都做完了，但 `ui.html` 一行没改——功能在界面上碰不到，
等于没做。这一阶段只解决"入口"：登录门、用户管理页、开关、提示。

### 分层

| 层 | 位置 | 职责 |
|----|------|------|
| 登录态 | `AUTH` 对象（ui.html） | 保存 whoami 结果：是否多人模式、当前用户、能否写、锁快照 |
| 登录门 | `bootAuth()` / `showLogin()` / `showSetupAdmin()` | 启动时先判登录；未登录整页换成登录卡，侧栏一并隐藏 |
| 用户管理页 | `viewUsers()` | 建号、勾岗位、改密码、删号；管理员不可删自己，避免把管理入口弄丢 |
| 协作开关 | `multiUserCard()` / `saveMultiUser()` | 设置页最上方的三个控件：使用方式、局域网、自动退出时长 |
| 状态提示 | `applyRoBar()` | 管理员被动只读时顶部常驻蓝条；普通用户显示自己的岗位范围 |
| 占用标记 | `lockTag()` / `lockOf()` | 题库列表行、组卷配额行标「某某编辑中」，该行加浅黄底色 |

### 关键决定

- **没登录就不给看侧栏**：登录卡是"整页顶掉"，不是浮层。分类树本身能说明单位有哪些业务，
  半开的界面（能看侧栏、点进去报错）比直接挡住更糟。
- **启动顺序不能反**：先把 `bootAuth()` 走完再 `loadState()`。反过来会因为 `/api/state`
  未登录被拒，界面先闪一屏"加载失败"，看上去像软件坏了。
- **`/api/settings` 与 `/api/ai/config` 补上管理员守卫**：这两个接口原来完全没挡，
  普通用户在控制台 POST 一个 `multi_user=0` 就把整套权限关掉了，岗位授权形同虚设。
- **用户列表不返回 `password_hash`**：前端一个字段都用不上，一旦被截图或被扩展抓走，
  等于把全体的口令离线爆破材料交出去。改为显式挑字段返回。
- **多人协作的三个控件不能用 `sMulti` 这类名字**：与"单位与默认值"里的
  「多选默认分值」`sMulti` 撞了 id，`getElementById` 取到的是分数输入框，
  保存出来的"使用方式"永远是空值，开关点了等于没点，界面上却看不出异常。改名为 `muMode/muLan/muMins`，
  并加用例守住"界面内不得有重复 id"。
- **占用标签不显示自己**：`lockTag()` 先比对当前用户名，否则会出现"我自己正在编辑我"。
- **定时轻量刷新只更新顶部条**：`pollAuth()` 每 20 秒取一次 whoami，只改 AUTH 与状态条，
  不重渲染当前页——重渲染会把正在填的表单冲掉。

## P37 退出登录常驻入口（2026-11-02）

起因是一句反馈：「我设置了管理员账号和用户账号，为什么登录默认都能看到？我没看到用户登录界面呢？」

现场查下来，授权、登录门、失效拦截全是好的，问题在**入口**：

- 他的浏览器里一直有有效会话（cookie），所以每次打开直接进系统，从不弹登录页；
- 而「退出登录」按钮只写在顶部只读条 `#roBar` 里；
- 只读条只在两种状态出现——管理员被普通用户挡住（只读）、或普通用户登录。
- 管理员正常使用时整条 `hidden`，于是**既看不到现在是谁，也找不到退出**，
  形成「出不来、也看不见」的死角。

### 改动

| 位置 | 改动 |
|------|------|
| 侧栏底部 | 新增常驻块 `#whoBox`：用户名 + 角色/岗位 + 「退出」 |
| `renderWhoBox()` | 唯一渲染入口；未登录或单机模式自动收起 |
| `bootAuth()` | 三条返回路径都同步一次（旧后端 / 单机 / 登录成功） |
| `pollAuth()` | 每 20 秒随 whoami 一起刷新，岗位变了这里能自己更正 |
| `showLogin()` / `showSetupAdmin()` | 整页顶掉时收起，避免登录页背后透出上一个用户名 |

只读条职责收窄为「陈述为什么只读」，不再兼作退出入口。

### 顺带纠一处误报

`CODE_FILES`（判断"磁盘代码比进程新，需要重启"）原先含 `ui.html`。
但页面走 `Cache-Control: no-store` 返回，刷新一定拿到磁盘新版，**根本不需要重启**；
把它算进来，导致每次只改界面也会弹一条「请双击停止/启动.bat」，而重启对界面毫无作用，
反而让人以为软件出了问题。

现只统计后端 `.py`。原先要防的场景（界面加了新按钮、后端还是旧进程 → 点了报
`not found`）必然伴随某个 `.py` 也变了，照样会被抓到，防护没有变弱。

### 用例

`tests/test_p35_ui.py` 增 2 项（19 项）：

| 用例 | 守住什么 |
|------|----------|
| `test_logout_entry_is_always_reachable` | 侧栏有用户块；bootAuth 成功后渲染；登录页/初始化页收起 |
| `test_stale_check_ignores_ui_html` | `CODE_FILES` 不含 `ui.html`，但必须含 `server.py` |

## P38 会话时长与「在线」判定同源（2026-11-02）

用户确认多用户规则保持现状（有普通用户在线时管理员只读），分工形态为「多人分岗位维护题库」。
顺着这个问题核对判定条件时，发现一处错位：

- 登录会话按设置页的「多久没操作自动退出」过期（`session_user` 的 minutes 由调用方传入设置值）；
- 但「谁算在线」`auth.online_regular_exists` 写死 `DEFAULT_SESSION_MINUTES = 30`；
- 而管理员是否只读、能否改分类结构，全都看这个函数。

后果：用户把时长改成 60 分钟后，同事已 35 分钟没动，系统仍认为他"在线"，
管理员被迫继续只读；反过来把时长调小（如 5 分钟），数值又对不上。
同一个概念在两处用两个数，属于迟早出问题的写法。

### 改动

`auth.setting_minutes(conn)` 作为唯一取值入口（读 `setting.session_minutes`，取不到退回默认 30），
`session_user` / `online_regular_exists` / `purge_sessions` 三处统一调用它。

行为对默认设置（30 分钟）完全不变，只在用户改过该项时才不同——所以没有回归风险。

### 用例

## P39 设置页按身份裁剪（2026-11-02）

用户一句话："系统设置里面的一些内容普通用户不需要看到，可以隐藏起来。"

之前的状态是「看得见、点得动、点完报错」：P36 接前端时把设置页整体做完了，
`viewSettings()` 一个函数同时服务两种身份，于是普通用户也能看到

- 多人协作开关（一改就改变全系统的使用方式）
- 单位与默认值（单位名、编号前缀、各类默认分值、备份保留份数）
- 分类维护（改名、增删二级）
- AI 接口与密钥（地址、模型、密钥尾号、超时）
- 数据与备份（数据目录、库大小、版本、立即备份、压缩）
- 备份记录（可一键恢复覆盖当前库）
- 清理（清空试卷 / 清空题库）

后端从 P35 起就用 `_admin_only` 挡住了这些写操作，所以不存在越权；
但界面上摆着一堆点了必失败的东西，比没有更让人困惑——用户会怀疑"是不是坏了"
或者"是不是我权限没配好"。这次把界面与后端口径对齐，隐掉，不是禁用。

### 改动

**前端（`ui.html`）**

| 位置 | 改动 |
|------|------|
| `isAdmin()` | 新增统一判定：`AUTH.on` 关闭（单机模式）视为管理员，老用法不受影响 |
| `viewSettings()` | 首行分流：非管理员直接返回 `settingsForRegular()`，**不再请求 `/api/backups`**；管理员分支保留原样，另加 try/catch 兜底（接口被挡时不能整页报错） |
| `settingsForRegular()` | 只渲染一张「我的账号」卡：姓名、身份、岗位分类（无则提示"未分配岗位，请联系管理员"）、自动退出时长说明、「退出登录」 |
| `renderNav()` | 「用户管理」的条件从 `AUTH.on` 收紧为 `AUTH.on && isAdmin()` |

**后端（`server.py` / `ai_parse.py`）**

| 接口 | 改动 | 理由 |
|------|------|------|
| `GET /api/backups` | 新增 `_admin_identity_only`，仅管理员可读 | 数据目录与备份文件名属于管理信息；恢复备份的入口就在同一块数据里 |
| `GET /api/ai/config` | 普通用户走 `ai_parse.brief_config()`，只给 `enabled/model/vision_model/ready` | 接口地址与密钥末 4 位不该发给普通用户；但导入页的引擎说明要读 `ready`/`model`，不能整块不给 |
| `POST /api/ai/test` | `_admin_only` | 拿真实密钥发一次请求，等于花管理员的钱 |
| `POST /api/ai/vision-probe` | `_admin_only` | 同上（一次视觉请求） |

`_admin_identity_only` 与原有 `_admin_only` 分开是有意的：后者含"管理员在有普通用户在线时只读"的让位规则，
那条规则针对**改数据**；查看备份列表什么都不改，管理员随时该看得见，否则一有人在线设置页就报错。

### 用例

新增 `tests/test_p39_settings_scope.py` 共 18 项：

| 分组 | 用例 | 守住什么 |
|------|------|----------|
| 静态（6） | `test_settings_splits_by_identity` | `isAdmin()` / `settingsForRegular()` / 首行分流三处都在 |

### 顺带修掉的显示缺陷（截图核对时发现）

改完直接截图核对界面，第一张就露出问题：普通用户顶部状态条与侧栏用户块写着
**「当前岗位：#1 · #2」**，而同一页面的「我的账号」卡里却是「电气 · 暖通」。

原因是渲染顺序：`bootAuth()` 先跑 `applyRoBar()` / `renderWhoBox()`，此时还没
`loadState()`，`STATE.cats` 是空的，`catName(id)` 只能回退成 `#id`；
等分类树到了没人再刷这两处（只有 20 秒一次的 `pollAuth` 会顺带纠正）。
代码本身逐字读没有问题，是"先画后取数"的时序，只有看渲染结果才发现。

"没登录就收起"的守卫，单机模式调用无副作用）。两条用例分别盯住"调用在"与
"显示出来的是中文名"。

## P40 文件夹版 exe（2026-11-05）

用户："软件目前的成熟度是否可以正常使用了，如果可以的话，我想还是需要你打包一下，采用文件夹版 exe 方案"。

先跑全量回归确认成熟度（531 项全绿、工作区当时干净、范围内需求均有实现与用例，
唯一范围外仍是 FR-PP-05 导出 Word），再动手。选 **onedir** 而不是 onefile：
onefile 每次启动要把 20 MB 自解包一遍（5~10 秒），onedir 一两秒就起来，
而且 `ui.html` 外置后改界面只换一个文件，不必重新打包。

### 三个不改就会出事的地方

**1）冻结后的路径基准。** 源码版 `BASE = os.path.dirname(__file__)`，
PyInstaller 下 `__file__` 指向 `_internal` 里的临时目录，若照旧，题库会被写进
 `_internal\data\`，重装/升级就没了。改为 `sys.frozen` 时以
 `os.path.dirname(sys.executable)` 为准，`DATA_DIR` 因此始终落在 exe 旁边。
 `ocr_win.py` 的 PowerShell 脚本定位同样处理。

**2）不能拿 `server.py` 当入口。** `ai_parse.py` / `paper_engine.py` 里有
 `import server as core`；若 server 自己就是 `__main__`，进程里会存在
 `__main__` 与 `server` 两份模块副本，`DB_PATH`、导入进度这些模块级全局量各有一份，
 变成"读 A 库写 B 库"。新增 `app_main.py` 只负责环境与异常兜底，
 再 `import server; server.main()`，保证 server 只被加载一次。

**3）`--windowed` 没有控制台。** `sys.stdout` / `sys.stderr` 是 `None`，
 `server.main()` 里的 `print` 会直接抛 `AttributeError`；任何启动异常都会静默闪退，
 用户只看到"双击没反应"。入口里给两者接一个空 Sink，异常写
 `data/startup_error.log` 并弹 MessageBox。

### 图标兼容性补记（2026-11-06）

用户反馈"exe 文件没有默认图标"。先查事实，别急着改代码：

| 检查 | 结果 |
|------|------|
| PE 资源表 | `RT_ICON` 7 帧 + `RT_GROUP_ICON` 1 项，图标**确实嵌进去了** |
| `ExtractIconExW` / `SHGetFileInfoW` | 都能提取出蓝底试卷 + 对勾的 logo，32x32 正常 |
| ico 文件本身 | 7 帧**全是 PNG 压缩数据**（`logo.ico` 是 Chrome 截图 + 手工拼 ICONDIR 的产物） |

结论：不是"没打包图标"，而是 **PNG 帧 ico 的兼容性**。Vista+ 虽支持 PNG 压缩图标，
但资源管理器图标缓存、部分旧系统/缩略图提取器对它支持不稳定，会退化成系统默认图标；
而本机 API 是新进程、重新读文件，所以查不出这个差异。同一路径反复覆盖打包又会放大缓存问题。

修法：不改动界面用的 `logo.ico`（P34 的 AC-23 明确要求它是七帧 PNG），
另出一份 **标准 DIB(BMP) 帧** 的 `assets/logo_exe.ico` 专供 exe：

- `tools/make_icons.py` 新增 `decode_png()`（纯标准库解 8bit RGBA、反 filter 0~4）、
  `dib_frame()`（BITMAPINFOHEADER + 自下而上 BGRA + 1bpp AND mask）、`build_ico_dib()`；
  `python tools/make_icons.py --dib-only` 可只用已有 PNG 重建，不需要浏览器。
- `tools/build_exe.py` 的 `--icon` 改指 `logo_exe.ico`；同时把 `logo.ico` 外置到包根，
  供桌面快捷方式手动指定图标；`使用说明.txt` 补上"图标没显示怎么办"。
- 新增静态用例 `test_exe_icon_uses_dib_frames`：逐帧断言 `biSize == 40`
  （PNG 帧开头是 `0x474e5089`），防止以后有人图省事又改回 PNG 帧。

复核：新 exe 的 7 帧 RT_ICON 头部全为 40；Win32 提取出的图标与旧版逐像素比对
仅 4.1% 边缘 alpha 差异，肉眼一致；启动 / 组卷 / 退出全链路复测通过。
