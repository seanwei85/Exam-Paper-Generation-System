# 多用户管理功能需求草案（评估稿 v0.1）

**状态**：草案，待评审。**日期**：2026-11-01
**背景**：现有系统为单机版本（浏览器界面 + 本机 SQLite），需求书 §2.3 明确将"多人协作与权限体系"列为**本期不做**，§3.1 定义单一使用者（题库管理员兼考核管理员）。本草案把该能力展开评估，供决定"做 / 不做 / 做到什么程度"。

---

## 1 这套功能面向什么场景、解决什么问题

先确认要解决的真实问题，再决定做不做。按必要性从高到低排：

| 场景 | 现在怎么办 | 多用户能带来的价值 |
|------|-----------|-------------------|
| 一个 team 在一台电脑轮流出卷 | 谁坐那台机器谁就是管理员，互相改来改去 | 低——本机账号登录反而多了记密码/切换/退出步骤 |
| 局域网多人**同时在线**查题、出卷 | 不支持，只能一个人开 | 高——题库共用、多人并发可读 |
| 多人同时**修改**题库（新增/导入/删） | 不支持，可互相覆盖 | 中高——需要并发写控制，否则乱 |
| 出卷/改题**要追责**（谁在什么时候改的） | 完全无记录 | 中——需要操作审计 |
| 外部分发、各位同事各管各的库 | 拷整个文件夹，各维护各的 | 低——多用户反而增加复杂度 |

**结论**：多用户的价值只在「局域网多人同时在线 + 需要权限与追责」时成立，而这已经是产品形态的升级（单机 → 局域网服务），不只是加个登录框。

---

## 2 范围界定

### 2.1 如果做，建议的最小闭环

- **账号体系**：管理员创建普通用户账号（用户名 + 密码），支持启用/停用、重置密码。
- **登录态**：浏览器登录，记住会话（cookie/token），关闭浏览器短期有效。
- **两种角色**：
  - **管理员**：全部功能 + 用户管理 + 数据备份恢复 + 组卷并发布试卷。
  - **普通用户**：看题库、组卷、打印；**不可**导入/批量修改题库、不可改系统设置、不可增删账号。
- **操作审计（可选进阶）**：记录"谁在何时对哪道题/哪张卷做了新增/修改/删除/采纳审校"，可在设置页查看。

### 2.2 明确不做

- 不做真正的并发编辑协同（同一时刻两人改同一道题并自动合并）——工作量与风险不成正比，仍用"占用校验 + 提示有人正在改"。
- 不做云端 / 互联网访问（仍是局域网）。
- 不做在线答题、交卷、自动阅卷、成绩统计（那属于整个"考核在线化"产品线，远超本次）。

## 3 功能需求（FR 级，供评审）

> 编号沿用需求书风格。P 为优先级。

| 编号 | 需求 | 优先级 |
|------|------|--------|
| FR-MU-01 | 用户管理：管理员可增/删/停用用户、重置密码；用户名唯一 | P0 |
| FR-MU-02 | 登录：登录页输入用户名密码；失败给出原因；无人登录时禁进功能页 | P0 |
| FR-MU-03 | 会话：登录态持久（关闭浏览器短期仍在）；提供「退出登录」 | P0 |
| FR-MU-04 | 角色权限：普通用户只读题库，不能导入、批量修改、删题、改设置、管用户 | P0 |
| FR-MU-05 | 管理员初始化：首次启动强制创建管理员账号，未设置前不可用 | P0 |
| FR-MU-06 | 密码安全：存储为加盐哈希（绝不明文存库）；密码框不回显 | P0 |
| FR-MU-07 | 并发提示：同题被他人修改时给出提示，避免静默覆盖 | P1 |
| FR-MU-08 | 操作审计：记录谁在何时改了哪道题/哪张卷（新增/修改/删除/采纳） | P1 |
| FR-MU-09 | 审计查看：设置页可筛选查看审计记录（按人/按时间/按操作） | P2 |

## 4 关键设计问题与取舍

| 问题 | 取舍建议 |
|------|----------|
| **数据存哪** | 沿用本机 SQLite，`user`、`session`、`audit_log` 三张表。仍是单文件库 |
| **登录凭证** | 上手维护成本与安全折中：本机服务用"会话 ID（随机）落 SQLite + 短期过期"，不上 OAuth / JWT 重武器 |
| **并发修改** | 不做 optimistic-lock 自动合并；用"保存时 if…update 版本号冲突则报错提示刷新" |
| **端口与绑定** | 默认仍 `127.0.0.1`（只能本机）；**只有主动勾选"允许局域网访问"**才绑 `0.0.0.0`，并在设置页显著警示 |
| **是否引入依赖** | 保持零第三方依赖：哈希用标准库 `hashlib.scrypt`/`pbkdf2`，会话用 `secrets` |
| **兼容旧库** | 旧库无用户表，迁移脚本初始化时建表并强制建管理员，已有题库/试卷数据不动 |

## 5 工作量与技术影响（粗估）

- 新增表：user / session / audit_log；迁移脚本。
- 后端：登录/登出/会话校验/用户管理/权限鉴权中间件 / 审计接口。
- 前端：登录页、用户管理页、审计查看页、各处按钮按角色显隐/禁用。
- **测试影响**：现有 UI/接口用例大量点击按钮，一旦加登录拦截，几乎全部要补"先登录"前置；预计新用例 40–60 项，存量用例需适配改造。
- 影响既有设计原则："零依赖、离线、零运维"会局部变成"局域网服务"；`启动试卷系统.bat` 与默认只本机访问的行为需谨慎调整。

---

## 6 建议

1. **缺明确场景就先不做**。若只是单机轮流出卷，账号体系纯属增加使用摩擦，看不到收益。
2. 若确实要多人**同时在线**，建议按 §2.1 的最小闭环做，并**显式维护"局域网绑定默认关闭"**以保住本机版的安全底线。
3. 优先级最高的不是登录，而是 **FR-MU-07/08（并发提示 + 审计）**——它们解决的是单机多人轮流改时"互相覆盖、无据可查"的真实痛点，且不破坏本机单用户定位。
4. 若只想要"不同的人各出一份卷、各人私有配置"，更轻的方案是**给用户/终端加配置隔离**，而不是整体账号体系——成本低得多。
